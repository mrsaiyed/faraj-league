This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm test                              # Run all unit tests (vitest)
npx vitest run tests/standings.test.js  # Run a single test file (also: tests/stats.test.js, tests/seasons.test.js, tests/api.test.js)

npm run seed      # Seed database with placeholder data

# Import a season's player names (idempotent; --sql prints SQL for the Dashboard instead)
node scripts/import-roster.js scripts/rosters/fall2026.json
node scripts/import-roster.js scripts/rosters/fall2026.json --sql > supabase/seed_fall2026_players.sql

# Deploy all Edge Functions at once
npx supabase functions deploy auth-login admin-export-csv admin-seasons admin-teams admin-players admin-games admin-awards admin-stats admin-sponsors admin-media admin-content admin-media-slots admin-game-stats admin-game-log

# Push DB migrations (apply in order: 001–016)
npx supabase db push
```

Tests cover `lib/standings.js` (`calcStandings`, `rankTeams` and its tiebreakers, `calcSeeds`, `conferenceStandings`), `lib/stats.js` (`aggregateStats`), `lib/seasons.js` (slug/ordering helpers), `lib/team-logos.js` (logo resolution), `lib/draft-bank.js` (player-bank search), `lib/roster.js` (display ordering), `lib/game-tracker.js` (live stat engine), `lib/sponsors.js` (sponsor slots), `lib/live-sync.js` (public live refresh), `lib/game-clock.js` (game status + clock), `lib/season-logo.js` (per-season hero logo), `lib/champion-photo.js` (per-season hero photo), `lib/trophy.js` (champions trophy cards, slots and card layout), `lib/jersey.js` (jersey-number parsing and duplicates), `lib/game-log.js` with `js/game-log.js` (game-log rows and their markup), `lib/game-rules.js` (the league's rules), `lib/db-errors.js` (the database's refusals in plain words) and `admin/js/autosave.js` (saving the play-by-play as it happens, on fake timers) — pure functions only, no DB. `admin/js/game-reset.js`, `admin/js/jersey.js`, `admin/js/game-log-store.js` and `admin/js/league-rules.js` (saving the rules, reading the Rules page's boxes, its standings preview) are tested against stubbed `adminFetch`, Supabase clients and storage. `tests/api.test.js` covers `getSeasonData`'s season scoping, `getChampionData`'s cross-season reads and `getGameLog` against a stub Supabase client.

No build step — this is a static site with ES modules served directly.

## Architecture

**Stack**: Static HTML/CSS/ES modules (no bundler) + Supabase (PostgreSQL + Edge Functions) + GitHub Pages hosting.

### Public Site

`index.html` → `js/app.js` (orchestration) → `js/data.js` (fetch) → `lib/api.js` (Supabase queries) → `js/render.js` (DOM updates).

Data flow:
1. `fetchSeasons()` populates the season dropdown
2. `fetchSeasonData(slug)` fetches all season data in parallel (teams, players, rosters, games, awards, stats, sponsors)
3. `transformSeasonData(raw)` maps Supabase shape → internal `config.DB` shape (run once on fetch)
4. `renderAll()` updates all page sections from `config.DB`
5. `changeSeason(slug)` repeats steps 2–4; `showPage(id)` toggles `.page.active`

### Admin Site

`admin/index.html` is the **public site + edit overlays** — same layout, same width, same nav. Admin logic adds edit controls to every editable region.

`admin/js/admin.js` handles login and `adminFetch(fnName, options)` — all writes go through Supabase Edge Functions with `X-Admin-Token` header (JWT stored in localStorage).

`admin/js/admin-data.js` is the admin counterpart to `js/data.js` — loads season data and hydrates `config.DB` for admin pages.

`admin/js/page-templates.js` contains HTML templates extracted from `index.html` so the admin mirror renders the same DOM structure. **Must stay in sync with `index.html`** — public render functions find elements by ID in these templates. Any structural DOM change in `index.html` (new IDs, section restructuring) must be manually mirrored in `page-templates.js`.

`admin/js/edit-overlays.js` attaches inline Edit buttons to content-block regions and handles the inline/modal editor UI.

`admin/js/sections.js` wires up all CRUD UI (inline edit overlays, modals, floating drawer for season/logout controls).

### Edge Functions (`supabase/functions/`)

All admin writes go through Edge Functions — never direct DB access from the browser:
- `auth-login` — validates password, returns 24h JWT
- `admin-{seasons,teams,players,games,awards,stats,sponsors,media,media-slots,game-stats,content,export-csv}` — CRUD handlers
- `_shared/auth.ts` — JWT verification shared across all admin functions
- `admin-game-stats` — saves `game_stat_values` rows **and** derives/updates `games.home_score`/`away_score` from point totals; this is why scores update when a stat sheet is saved. It sums each row by its own `team_id` (migration 015), so a player moved since still counts for the side they played for
- `admin-game-log` — saves (upserts whole) or deletes a game's play-by-play in `game_logs` (migration 013)

Public reads use the Supabase anon key directly from `lib/api.js`.

### Non-obvious Behaviours

**Seasons**: `seasons.is_current` marks the active season — the public site loads it by default (`activeSeasonSlug()` falls back to the newest season if none is flagged). Migration 010 adds a partial unique index so only one season can be current; `admin-seasons` therefore always clears the flag on every other season *before* setting it, never the other way round.

**Creating a season**: the admin drawer's "New season" form posts `{ create: true, label, slug, is_current, total_weeks, copy_from_season_id, copy: { settings, teams, sponsors } }` to `admin-seasons`. The copy options carry `content_blocks` structure keys, team rows (names/conferences/captains, no players or rosters) and sponsor rows across from an existing season, so a new season starts with the same categories rather than blank. Per-season results (schedule, playoffs, draft, power rankings, awards, hero/season tag copy) are never copied.

**Roster imports are season-scoped by construction**: the generated SQL `CROSS JOIN`s the VALUES list against `seasons` filtered by slug, so a wrong or missing slug inserts zero rows rather than writing players into another season. The duplicate check is `season_id` + `lower(name)`, so the same person can appear in several seasons (they get one `players` row per season) while a re-run never doubles up within one.

**Live stat tracker (admin only)**: the "Live stats" button on a game opens `admin/js/live-tracker.js`. It records an append-only event log (score / foul / unfoul / sub / lineup / period / timeout / arrow) and derives everything from it, so undo and redo are just a cursor and can never drift from the totals. The log is held in `localStorage` per game (`faraj_live_tracker_<gameId>`), so a refresh or a locked tablet mid-game loses nothing, and is also saved to the database as the game's play-by-play (see **Game logs** below). Saving derives totals and posts them through the **existing** `admin-game-stats` function, which already recomputes the final score — so the totals need no new table, Edge Function or migration. It keeps points; the 3s, 2s and 1s made, counted from which of +3, +2 or +1 was tapped (the engine's `fg3`/`fg2`/`fg1`); fouls; and minutes (`STAT_SLUGS`): rebounds, assists, steals, blocks and turnovers were dropped as not needed, and an older log's `stat` events still load but count for nothing and stay out of the play log. Each is saved only if the league has its stat column (`points`, `3s_made`, `2s_made`, `1s_made`, `fouls`, `minutes`); migration 014 creates them all, or the admin Stats tab does one at a time (it makes the made slugs of the names "3s Made", "2s Made", "1s Made"). A missing one is named in a warning when the tracker opens and again on Save. The made counts ride the live push with the points they come from (one more row per basket), and points are sent first. Roster players who never appeared are sent as `dnp_player_ids`. Input is a tap on the player: their options open under the tile — +1, +2, +3, Foul and −Foul, as big buttons — and a bench player's also list who they come on "In for", one button per player on the floor, so a sub is two taps. Tapping anywhere else, or Escape, closes them; until a team's starting five is set, a tap picks it instead. Dragging a bench player onto whoever is coming off still subs — Pointer Events, not HTML5 drag-and-drop, because iOS Safari does not fire the latter. The options sit absolutely in the tile's own box (`.lt-slot`), so opening them never moves a tile, and `placeMenu()` keeps them inside the court: capped at its width, nudged in from its edge (measured in `offsetWidth` units, because of the desktop `html{zoom:1.1}`) and scrolled into view where the court scrolls on its own.

**Who played**: a player played a game if they have stat rows for it and are not in `game_dnp`. The live push writes a zero row for everyone on both rosters, so Save **and End game** send the roster players who never got on the floor (`didNotPlay()`) as DNP, which deletes their rows; before End game did this, a game ended but never saved counted as played for the whole bench.

**A player who leaves a team mid-season keeps everything they scored for it**: replacing a player is a roster change — the new player takes the old one's roster row (Fall 2026: Ali Mohsin in Hanny Ali's place on Raad, by `supabase/raad_fall2026_ali_mohsin.sql`), and the old one stays registered for the season, on no team. That script also registers Ali Mohsin as the same person as Spring 2026's Ali Mohsin Raza: the names differ, so the link-by-name trigger would have made a new person, but a registration inserted with a `person_id` keeps it. Their stat rows are never touched, and each already records the team it was scored for (`game_stat_values.team_id`, migration 015), so the site reads that rather than the roster: `aggregateStats()` counts every row for its own team and lists a player on no roster under the team of their latest game; each team carries `formerPlayers` (`formerPlayers()` in `lib/stats.js`: who played for it, is no longer on its roster, and in which games), so `renderBoxScore()` still lists them in those games — and a player now on one side who played a game for the other is listed only where they played. Before this, the stats page and the box scores read the team from the roster alone, and a player taken off one simply disappeared from both. The stats views (migration 016) always used `team_id`.

Both admin stat sheets list former players under the side they played for, **read-only** (`formerSheetPlayers()`, `statSheetRow()` in `admin/js/sections.js`): Save skips disabled boxes, so their lines are never sent — `admin-game-stats` takes only players on the rosters, and would refuse them — and "Clear game" leaves them alone. The sheets also tick DNP for a roster player a game with stats has no line for (`markJoinedSince()`): every save writes a row for each player who played and marks the rest DNP, so such a player joined afterwards, and their empty boxes would otherwise be saved as 0 — a game played. A former player is in the admin's player bank (they are on no team) and can be put back on one.

**Team fouls and the bonus are per half, and the badge goes on the other team**: `teams[id].fouls` is the whole game (the box score); `teams[id].halfFouls` is what the bonus runs on, and a `period` event clears it for both teams. `bonusLevel(halfFouls, rules)` is 1 at the league's `bonusFouls` and 2 at its `doubleBonusFouls` (the Rules tab; 7 and 10 when it says nothing, and a double bonus of 0 means there is none), and the tracker greys out a player at its `foulOutFouls` (5). `bonusFor(state, teamId, opponentId, rules)` deliberately returns two different things: `penalty` is that team's *own* foul trouble, which is what makes their count grow on screen, while `bonus` is what they *shoot* and comes from the **opponent's** fouls. Reading one for the other puts the "Single Bonus" badge on the team that committed the fouls, which is backwards. The `period` reset is guarded on the number actually changing, so a repeated "we are in period 2" event cannot wipe fouls already committed in it.

The horn sounds on the **crossing only**: the tracker keeps the level it last painted per team and fires only when it rises, so a repaint at 8 fouls is silent while the 7th sounds. It is primed after the first paint, so reopening a game already in the double bonus shows the badge without blaring. Half time lowers the level in silence, and the next 7th foul sounds again. Because the horn is a nicety and the badge is the real signal, every audio path swallows its own errors and a flash message names the team as well.

**−Foul takes back a foul after the fact**: Undo only reaches the last thing recorded, so a foul found to be wrong later, once more has happened, needs an event of its own. `unfoul` takes back that player's **most recent** foul: one off the player and one off the team's game total always, but one off `halfFouls` only if that foul was committed in the current period — `deriveState()` keeps each player's foul periods in `foulPeriods` for exactly this — so taking back a first-half foul in the second half cannot drop the other team out of a bonus earned in this one. It is an event like any other, so Undo takes a −Foul back as well, and the play log reads "Foul taken back". With no foul to take back it counts for nothing and leaves a warning; the tracker disables the button at 0 fouls. A −Foul that brings a team back under 7 lowers the bonus in silence, as half time does.

**Timeouts and the possession arrow**: each court has a **Timeout** button beside the team fouls, showing what that team has left as dots (●●○, or "n left" past six). A tap records a `timeout` event for the team and stops a running clock, publishing the stop so viewers see it; a team with none left can still be given one — the tracker records what happened — but only after a confirm. The engine only notes the period each timeout was taken in; how many a team has is the league's rule, `content_blocks.game_rules` (JSON text, **null `season_id`**, so league-wide), set on the admin's **Rules** tab: so many a **game** (what is left carries into overtime, plus any extra per overtime) or a **half** (each half starts afresh, and each overtime gets only its extra). With no block it is 3 a game and nothing extra (`DEFAULT_GAME_RULES`). The tracker reads the rule when it opens, and its **Timeouts** button (labelled with the rule in short, "3/game") changes it **for that game alone** — before tip-off, typically: the change is kept in the game's tracker session (`session.rules`, this device's localStorage; null means the league's), never written back to the league setting, and survives **Mark not started** like the period length and colours do. Setting it to what the league already says stores nothing, so a later change to the league rule still reaches that game. Halves and overtimes are the tracker's only periods, so a per-quarter rule would need quarter periods first. `admin-content` only writes keys on its `validKeys` list and answers ok for any other, so `game_rules` needed adding there and the function redeploying; `saveGameRules()` reads the row back and says so rather than claiming a save that did not happen.

The ◀ ▶ under the clock (beside it on a phone lying down) is the alternating-possession arrow: an `arrow` event points it at a team, so setting it after the opening tip and flipping it once it is used are the same tap, and Undo takes either back. The side it points to is lit in that team's colour, and the team is named beside it, because on a phone held upright the away team sits under the clock rather than to its right. The engine never flips it on its own (at half time, say) — leagues differ on what starts a half. Both kinds of event go in the game log, named by team (`describeEvent()`'s `teamNameOf`; the log hides its team column on a phone), and only the admin's log lists them: they are behind no stat column (`visibleLogTypes`).

**Jersey numbers are entered in a panel down the tracker's left side, and belong to one season**: the **Jersey numbers** button (its badge counts the players with no number yet, and turns red with `!` while a typed number is not saved) opens `#lt-jn`, a drawer listing both teams in roster order, a box per player, over a dimmed tracker (two columns when it is wide enough, stacked on a phone held upright). **The period picker is a jump, not a rewind — undo is what actually goes back**: the tracker's `<select id="lt-period">` (`PERIOD_OPTIONS` in `lib/game-tracker.js`: H1, H2, OT1, OT2, OT3) lets a scorekeeper pick any period directly, including straight to OT without stepping through every period between. Picking one **appends** a `period` event the same way scoring or a foul does — it never moves the undo cursor — so nothing already recorded is erased by a period change in either direction; Undo is the only thing that removes events, including a period change made by mistake. Picking a period also sets the clock: a half to the game's half length (`session.periodSeconds`, which starts at the league's `halfMinutes` and grows if the clock is set longer), an overtime to the league's `overtimeMinutes`.

This is also the fix for a real bug: `session.period` used to be a plain counter the old advance-button only ever incremented, so undoing back out of a period it had moved into rolled the score back correctly but left the picker — and the period stamped on every event recorded after — stuck on wherever it had last been pushed forward to. `render()` now re-derives `session.period` from `deriveState(...).period` on every paint instead, so it always matches whatever the undo cursor is currently pointing at, exactly like the score and fouls already did. `bonusFor()` was never affected by this, since it already read `halfFouls` off the derived state rather than off `session`.

Clearing a game (see below) resets this local `session` too — period, clock and status all back to blank, keeping only a deliberately customized period length and the team colours — or a freshly cleared game would still show whatever period/clock it was left on, which reads as if the clear hadn't worked even though the database is correctly reset.

Several things about it are not obvious:

- **The stage is pinned by JavaScript, not `position:sticky`**, and that is because `position:sticky` does nothing anywhere on this site: `body{overflow-x:hidden}` makes body a scroll container that never scrolls, so sticky descendants never stick — the nav's own `position:sticky` is inert for the same reason. `readScroll()` toggles `is-pinned` / `is-past` on every scroll event.
- **Until the stage pins, part of it is below the window**: at the top of the awards page by the nav's height, and at the bottom of the home page by however much has yet to scroll into view. `placeCamera()` shifts the shot (`setViewOffset`) to centre the ball on the visible part, capped so the ball never rises past the stage's top edge. The scroll cue rides up with the bottom of the window (`--trophy-pre`), and `--cue-room` fades it out while the ball still reaches down over it — otherwise "Scroll" is printed across the ball as the home trophy arrives.
- **The desktop `html{zoom:1.1}`** makes `getBoundingClientRect()` values 10% larger than `offsetHeight` and leaves `100vh` 10% taller than the window. Scroll progress converts to rect units, and the stage height comes from `innerHeight` when the zoom is active.
- **Each material gets the environment map itself.** With `scene.environment`, three.js (r186) overwrites every material's `envMapIntensity` with `scene.environmentIntensity`, so the matte-black base reflected the whole studio as charcoal grey.
- **Engraving ink is occluded** (R channel of the plate's packed occlusion/roughness/metalness texture): even near-black metal picks up a colour-independent Fresnel sheen, which lit the letters from inside.
- **Cards open on `click`, not `pointerup`.** On touch the browser fires its click after the finger lifts, at whatever is under it by then; opening on pointerup put the overlay there first, and the click closed it instantly.
- **The card font must be loaded before textures are drawn.** `loadCardFont()` waits for the Jost stylesheet itself before `document.fonts.load()` — one shared wait, since the hero plaque and a trophy can both ask at page load and the second caller must not find the `<link>` already there and skip ahead; without the `@font-face` rule, `fonts.load()` resolves at once and the plates get engraved in the fallback font (the HTML card, which re-renders when a font arrives, would still look right).
- **One import only.** three.js's add-ons import `'three'` themselves; to rule out a CDN ever loading two copies, the studio environment is built in (`studioScene()`) and the base uses plain boxes.
- **The ball's seams are fitted to the photo of the real trophy.** `BALL_SEAMS` in `js/trophy.js`: two great circles (`cross`, `middle`, nearly perpendicular) and two side rings (`upper`, `lower`), each "asin(n.p) = lat + k (m.p)^2" — a circle round an axis, squeezed slightly along one direction, which is what lets the lower ring run off the bottom right as the real one does rather than curling back. The photo's four seam lines were traced and the curves fitted so the site's **upright front view** draws them in the same places (appearance, matched through the site's own camera, not the photo's lower, closer viewpoint); the sides, back and top follow from the same curves. Keep them in the trophy's frame (+x right, +y up, +z out of the front).
- Jost stands in for the real plates' Futura; `CARD_TRACKING` (0.035em) makes up Futura's extra width so line lengths match the real card. Card and plaque proportions were measured off the photo of the real trophy.

**A game is only "won" when it is final**: `games.status` (migration 012) distinguishes scheduled / live / halftime / final. Before it, a card showed a winner the moment either team scored, so a live game read as finished as soon as one side led. `gameStatus()` treats a NULL status with scores as final, so everything recorded before 012 still shows its result. While live, the winner tag's slot carries the period and clock instead; `js/app.js` ticks those once a second from `displayClockSeconds()`, which extrapolates from `clock_updated_at`, so the tracker writes the clock only on start/pause/period/end rather than every second. The tracker marks a game live on its first recorded event, halftime at the first-half buzzer, and final via its **End game** button; `clearGame()` resets the status too, or a cleared game would keep showing a running clock.

**The probe selects `*` deliberately**: naming columns there makes the entire query fail against a database that has not run a migration yet — PostgREST answers "Could not find the 'clock_running' column of 'games' in the schema cache" — and since `probeScores()` bails on any error, live refresh dies completely and silently. Only a manual reload works, because the full read already used `select('*')`. Never name a newly added column in the probe. The tracker likewise treats a schema-cache error from its clock push as "this database predates migration 012", stops pushing, and says so once instead of flashing a save failure over the stats status, which is saving fine.

**The two fingerprints must agree**: `scoresFingerprint()` decides whether the probe re-reads, `liveFingerprint()` decides whether to repaint. `liveFingerprint` is built on top of `scoresFingerprint` for exactly this reason — when they diverged, a game going live, a period ending or the final whistle was fetched and then silently dropped, because the score itself had not moved. A test pins them to the same set of changes.

**Live scores on the public site**: the tracker pushes to `admin-game-stats` ~0.9s after the last tap (and on undo/redo), sending **only the rows that changed** since its last successful write (a failed push is retried every `RETRY_MS`, 10s, until one lands, so the last basket of a game never waits for a tap that never comes) — the function upserts sequentially, one round-trip per row, so resending the whole zero-filled roster every tap would take seconds. The public site runs a cheap probe (`getGameScores`, one small `select('*')`) every `SCORE_POLL_MS` while the tab is visible, and re-reads the whole season only when `scoresFingerprint()` moves; a slower `FULL_POLL_MS` sweep catches changes the probe cannot see (rebounds, a corrected box score). Measured end to end at about 4s from tap to a viewer's screen. It holds off while a box score or the nav drawer is open. Neither side needs a new Edge Function or migration.

`scoresFingerprint()` accepts raw `games` rows and transformed `config.DB.scores` alike and yields the same string for the same game. That matters: the probe's baseline is seeded from the data already loaded, not from the first probe — seeding on the first probe silently swallows any score that changes between page load and it.

Two traps this depends on. `toStatValues()` takes the full roster so it can emit explicit zeros — without them, undoing a player's only basket drops them from `state.players`, no row is sent, and the stale total survives on the server. And `hasRecordedStats()` gates every push, because zero-filled rows are never empty and setting lineups alone puts players in the map with court time: pushing those would write 0-0, which the site reads as played.

**Clearing a game**: emptying a stat sheet and saving leaves the score at 0-0, and since every "has this been played?" test is `score !== ''`, `'0'` still counts — the game stays complete and scores as a tie. `clearGame()` in `admin/js/game-reset.js` is the way back: it deletes the stat rows (by naming the whole roster as DNP, which is the only delete lever `admin-game-stats` exposes), empties `game_dnp` again, then nulls `games.home_score`/`away_score` via `admin-games`, and last deletes the saved game log via `admin-game-log` — quietly skipped where that is not deployed, since the game is already back to not played by then, but needed: a game cleared and then filled in from the stat sheet would otherwise show the old game's play-by-play. The tracker's **Mark not started** button runs it (so does saving with nothing recorded), and the stat sheet has a "Clear game" button. The tracker first cancels a queued push, waits for one in flight and holds new taps until it is done — status pushes run one after another through `statePush` so there is a last one to wait for — or a basket tapped a moment earlier, or the "live" it set off, lands after the reset and undoes it.

**Minutes played** are derived from an `elapsed` stamp (cumulative seconds the clock has actually run) carried on every tracker event, not from the countdown — so setting the clock **forward** never adds anyone minutes. Setting it **back** within a period does take them back, because that nearly always means the clock was left running through a stoppage: `rewindClock()` winds `elapsed` back by the time put on the clock (never past `periodStartElapsed`, which `deriveState()` records at each period change) and moves every event stamped after that moment onto it, elapsed and clock reading both. So the players on the floor lose exactly those seconds, one subbed on during the stretch starts from the corrected moment, and one subbed off stops there; what was recorded in the stretch still counts. That restamp is the one edit the event log ever takes, and it is outside undo — setting the clock again is how to correct it. A stint is banked when the player leaves the floor; `livePlayerSeconds()` adds the open stint so a starter who is never subbed does not read as zero. Minutes are saved as the `minutes` stat, in whole minutes as a box score shows them (whole numbers also keep season totals free of float noise, since the stats page prints values as they are), but **only on End game and Save**: court time grows every second the clock runs, so carrying it on the tap-driven live push would add a round-trip per player to each push and hold up the score viewers are waiting for. End game first waits out a push already on its way, because a call made while one is in flight folds into the next tap push, which carries no minutes.

**Season scoping**: `rosters`, `player_stat_values`, `game_stat_values` and `game_dnp` have no `season_id` — they are reached through `team_id`/`player_id`/`game_id`. `getSeasonData` therefore runs in two passes: season-scoped tables first, then those tables filtered by the ids it just fetched. Anything querying them must do the same or it will read across seasons (and eventually hit PostgREST's 1000-row cap). `stat_definitions` is deliberately global — every season shares the same stat categories.

**`confLabel()` vs `confLabelRaw()`**: `confLabel()` returns HTML with brand-name `<span>` highlights — use only in `innerHTML` contexts. `confLabelRaw()` returns plain text — use in `textContent`/attributes. `highlightSponsor()` only wraps three specific brand names (TOYOMOTORS, XTREME, Wellness).

**`scheduled_at` timezone**: `datetime-local` inputs in the admin produce naive `YYYY-MM-DDTHH:mm` strings (no timezone). `scheduledAtInputToIso()` in `sections.js` converts them to full ISO strings using the browser's local timezone offset, so times are stored correctly in UTC.

**`content_blocks` key precedence**: `transformSeasonData` applies global (null `season_id`) blocks first, then season-specific blocks, so season-level entries override global ones for the same key.

**`getBasePath()`**: Returns `/faraj-league` on GitHub Pages project sites (hostname contains `github.io`), otherwise `''`. Used when constructing image URLs so assets resolve correctly in both environments.

**Seeds are league-wide, and the tables are still grouped by conference**: the `#` column on the standings page and on the home page's standings preview is each team's seed in the **whole league** — 1 to however many teams there are, across both conferences — not its row position in its own conference, so one conference's rows might read 1, 3, 5 and the other's 2, 4, 6. The order is wins, then **the season's** tiebreakers, in the order set for it on the admin's **Rules** tab (`tiebreakers` in that season's `game_rules` row; see `seasonRules()`): head-to-head record, then point differential, then points scored unless the season says otherwise, and teams level on everything keep the order they are listed in. A line under the tables (`#standings-tiebreak-note`, in all three copies of the standings markup) says what they are, since head-to-head can put a team above one with a better differential.

Head-to-head is why the ranking is `rankTeams()`, a tied group at a time, not a comparison of two teams for `sort`: it counts only the games **between the tied teams**, so it depends on who else is tied. It applies once every tied team has played at least one of the others (until then it is skipped, rather than ranking a team on games it has not had the chance to play), and is the win percentage in those games. A tiebreaker that separates some of a group but not all of it leaves smaller ties, and each of those **starts again from the first tiebreaker** — so of three teams level on wins, one may go clear on head-to-head and the other two be settled by their own game. Forfeits count in head-to-head as they do in the standings. Other tiebreakers on offer: head-to-head point differential, and fewest points allowed.

**Each season keeps its own tiebreakers**, so changing them never re-ranks a season already played. Head-to-head came in with Fall 2026; Spring 2026 was decided on point differential, then points scored, and keeps that — under head-to-head its Dukhaan (who beat Noor) would be 3rd and Noor 4th rather than the other way round. Neither season has a stored row; `SEASON_RULES` in `lib/game-rules.js` records what each was played under, and a season's own row (saved from the Rules tab with that season picked) wins over it. A new season starts on head-to-head (`DEFAULT_TIEBREAKERS`), or the league row's tiebreakers if it has some; `admin-seasons` does not copy `game_rules` when it copies a season's settings.

`conferenceStandings()` builds a conference's rows, and `renderHome()` and `renderStandings()` (both of its branches) go through the same `confStandingRows()`, so the two views cannot disagree. Until a game has been scored every seed is `'TBD'`, and the `#` column shows a dash rather than positions that mean nothing (the Teams page shows `TBD` in the same state). Everything else that reads a seed follows: the Teams page's "Seed" and its order within a conference, the awards MVP ladder's tiebreak (seeds used to restart in each conference, so two teams from different conferences could tie on "seed 1"), and the stats page's team tiebreak, which reads the seeds too, so it cannot rank two teams the other way round from the standings. A team with no conference (or one the tables do not list) is still ranked in the pool, so it can use a number the tables do not show. **Postseason** (`lib/playoffs.js`): every week ticked "Playoff Week" in the schedule editor (`playoffs_by_week`, value `true`) is left out of the standings, but only the **last** ticked week is drawn as the bracket (`isBracketWeek()`); an earlier ticked week is a **play-in**, shown as ordinary games. With a play-in (Fall 2026: week 6 play-in, week 7 bracket) the bracket is seeded from it, not from the standings: the play-in pairs seeds 1 v 2, 3 v 6 and 4 v 5; the 1 v 2 winner is bracket seed 1 and its loser seed 2; the other two winners are seeds 3 and 4, the better regular-season seed third (`playInSeeds()`). Semifinal 1 (game 1) is 1 v 4, semifinal 2 (game 2) is 2 v 3, game 3 the championship. A bracket game not yet scheduled shows its seeds and who decides them ("Winner of Mujahideen vs Dukhaan") until the play-in or semifinal settles the team (`bracketSlots()`); once the admin schedules it, the real game card replaces it. Without a play-in week (Spring 2026) `renderPlayoffBracket()` is as it was: whatever games the admin scheduled, labelled "Conference Final" and "Championship". Encoding the play-in as an earlier `true` week rather than a new value keeps `game_stage()` (migration 016) counting it as playoffs, with no migration or `admin-content` redeploy.

**Fouls, minutes and the 3s/2s/1s made are recorded but admin-only**: the tracker saves them like points, but the public box scores and stats page show only `config.PUBLIC_STAT_SLUGS` (points). `visibleStatDefinitions()` in `lib/stats.js` filters at render time — `renderStats()` and `openBoxScoreFullscreen()` both go through it — and the admin sets `config.SHOW_ALL_STATS` on load to see every column. It filters when drawing, not when loading, because the tracker reads `config.DB.statDefinitions` to know where to save fouls and minutes. The stats page also decides who is listed from the columns on show, so a player with minutes but no points is not a row of dashes on the public table. To make a stat public, add its slug to `PUBLIC_STAT_SLUGS`.

**Game logs (the play-by-play)**: the tracker's event log is saved per game to `game_logs` (migration 013: `game_id`, `log` jsonb `{ version, events, names }`, `updated_at`) through `admin-game-log`, and shown under a **final** game's box score on the public site and under both admin stat sheets (`openStatSheet()` and the Games tab's). It is a scrollable box with each period's heading pinned to its top — `position:sticky` works there because the box is the scroll container, unlike the page itself (see the trophy notes). The public box score lists only the plays behind its public stat columns (`visibleLogTypes(config.PUBLIC_STAT_SLUGS)`: scoring, for now), the admin every play, and the public site reads a log only when a final game's box score opens (`fetchGameLog()` → `getGameLog()`), never in the season load. A database without migration 013 just shows no log; the admin says why.

What is saved is the session's events **up to the undo cursor** (`effectiveEvents()`), whole each time, with a snapshot of player names so the log still reads if someone is renamed. **It saves itself as the game goes, like the stats — no button.** Every change to the log (a play, Undo, Redo, the clock set back) saves it `LOG_SAVE_MS` (1.5s) later, after the score push viewers are waiting on, so a run of taps is one save (`createAutosave()` in `admin/js/autosave.js`). Saves run one after another, each sending the log as it is when its turn comes, so an older one never lands after a newer one. A failed save is retried every `RETRY_MS` (10s), or with the next tap, until it lands, and meanwhile a red line under the scoreboard (`#lt-log-note`) says the play-by-play is not saved yet; it goes once a save lands. Period changes and the half-time buzzer save at once, and so does the tab being hidden (a tablet locked, an app switched to), since a hidden page may never run its timers. End game and Save always send it and say in their message whether it landed; Close sends only what is unsaved, so opening and closing an old session never replaces a log another device saved. Mark not started cancels a waiting save and waits out one on its way before the clear deletes the log, or it would be put straight back. A failure never blocks scoring.

It used to be sent only at those breaks. Fall 2026's weeks 1 and 3 have no play-by-play: they were scored before logs were saved at all, so the scoring device held the only copy and never sent it. Do not go back to saving at breaks only — a device holding the only copy is how logs are lost.

`gameLogRows()` replays the events through `deriveState()` one prefix at a time, so the period, the running score and which events count are exactly what the tracker showed: a sub for someone not on the floor, or a −Foul with nothing to take back, counted for nothing there and is left out here. A period with nothing to list gets no heading. Headings are spelt out ("First Half", "Second Half", "Overtime") because Cinzel's "1" reads as a capital I.

A log that still never reached the database (tracked before logs were saved, or on a device that went offline and was closed) is sent from the device that holds it in two ways. **Opening the game in the tracker** sends it at once when nothing is saved for the game, or the saved log is the start of this one (`extendsSavedLog()`: the same plays, matched by type, player, team and the moment recorded, and this one has more) — never for a game since put back to not started, and never over a log that went further or another way. **Opening the admin** runs `uploadStoredGameLogs()` in the background for final games: a device log goes in when nothing is saved (even one that does not replay to the recorded score — the stat sheet was corrected after the game, say — since a log not quite right beats none; this used to be skipped silently, which is how logs were lost), when it carries on from the saved one, or when it replays to the recorded score (`logMatchesScore()`) and the saved one does not. A saved log that matches the score or holds plays the device does not have stays.

**Standings PD column**: `calcStandings()` returns `{ w, l, pf, pa }` — it does NOT include point differential. The PD column in the standings table is computed at render time in `renderStandings()` as `pf - pa`.

**Stats display limits**: `renderStats()` caps the table at 15 players (sorted by total points). A separate top-3 PPG leaders widget (`#stats-leaders-wrap`) is rendered above the table, sorted by points-per-game. Both respect the team filter.

**`config.DB` scores shape** (after `transformSeasonData`): `{ week, game, gameId, t1Id, t2Id, t1, s1, t2, s2, scheduled_at }`. The `t1`/`t2` fields are team names (used for display and standings lookups); `t1Id`/`t2Id` are DB UUIDs.

### Database Tables

`seasons`, `people`, `franchises`, `teams`, `players`, `rosters`, `games`, `game_stat_values`, `game_dnp`, `game_logs`, `awards`, `stat_definitions`, `player_stat_values`, `sponsors`, `media_items`, `media_slots`, `content_blocks`, `login_attempts` (rate limiting).

Season-scoped (`season_id` column): `teams`, `players`, `games`, `awards`, `sponsors`, `media_items`, `media_slots`, `content_blocks` (null `season_id` = global). Global: `people`, `franchises`, `stat_definitions`, `login_attempts`.

**Career history (migration 015)**: `people` is one row per real person and `franchises` one row per club, across seasons; `players` is a person's *registration* in one season (`players.person_id`) and `teams` a club's entry in one season (`teams.franchise_id`). Both tables hold only an id: a person's name is their latest registration's, a club's its latest season's team name (`people_directory`, `franchise_directory`), so the admin, which edits `players` and `teams`, stays the only place names are written. Nothing in the app sets the links: triggers do, by name (`name_key()`: case and spacing ignored). A new registration joins the person registered under that name in another season (the most recently active, if two), else becomes a new person; someone already in that season is never picked, so two people with one name in one season stay two. Renaming a registration that is its person's only one (a typo fixed after entry) moves it to the person the new name matches; a person with several seasons keeps the link, as that is just one season's spelling. A person or club left with no rows is deleted. Teams work the same way, so a new season's copied teams join their clubs. A wrong match is fixed in the SQL editor with `merge_people(keep, merge)`, `split_person(registration)` or `merge_franchises(keep, merge)` (none callable through the API).

`game_stat_values.team_id` is the team the player was on for that game, set by trigger from the roster when the row is first written and never rewritten by an upsert (it is not in the update), so moving a player later leaves their old games where they were. The trigger refuses a row for a player on neither team.

**What the database refuses (migration 015)**: deleting a player who has stats, a team that has games, or a season with recorded stats (`ON DELETE NO ACTION`; these used to cascade and silently erase history — deleting a game, which the admin warns about, still takes its stats with it); a roster row on a team of another season, or a player on two teams; a game between a team and itself, with teams of another season, or in a week and game number already taken (`games_one_per_slot`); two teams of one name in a season (`teams_season_name_key` — the site looks teams up by name); negative scores or stats; and a second `content_blocks` row for a key in a season (`admin-content` used to keep inserting copies once there were two; it now updates first). `admin-players` deletes the player before touching their captaincy, so a refused delete leaves them as they were. The admin shows each refusal in words (`lib/db-errors.js`).

**Stats views (migration 016)**: `player_game_stats` (one line per player per game: team, opponent, result, stats as columns), `player_season_stats` (per player, season and team), `player_franchise_stats` (per player and club, across seasons), `player_career_stats`, `team_game_stats`, `team_season_stats`, `franchise_stats`, plus `people_directory` and `franchise_directory`. Totals count only games that are over (`game_is_final()`, the site's rule) and come in three rows, `stage` = `regular`, `playoffs` (the season's `playoffs_by_week` content block) or `all`. Averages are over the games where that stat was recorded (fouls, minutes and the 3s/2s/1s only since the tracker saved them), and per-minute rates use only games with minutes. They are plain views (`security_invoker`, so they show anon only what the tables already do) and read nothing the site does not; a new stat column needs adding to `player_game_stats`. Manual season totals (`player_stat_values`) are not in them.

RLS allows public read on all tables; writes are enforced by Edge Function JWT validation, not RLS policies.

`config.DB` extended shape after `transformSeasonData`: `gameStatValues` (`{ [gameId]: { [playerId]: { [statDefId]: value } } }`), `statDefinitions` (game-scoped stat columns), `draftBank` (unrostered players), `draftTeamOrder` (from `content_blocks.draft_team_order` or team sort order).

`content_blocks` stores freeform JSON values by key. Schedule-specific keys: `schedule_week_labels` (week heading text), `schedule_slots_by_week` (per-week game slots), `schedule_dates_by_week` (per-week date strings). Conference keys: `conferences_layout` (JSON with `conferences[]` array), `conf_name_mecca`, `conf_name_medina`. Other keys: `hero_badge`, `about_text`, `draft_recap`, `draft_team_order`, `media_layout`, sponsor tier labels, and `game_rules` (the rules, set on the admin's Rules tab — JSON `{ timeouts, timeoutsPer: 'game'|'half', overtimeTimeouts, tiebreakers: [...], bonusFouls, doubleBonusFouls, foulOutFouls, halfMinutes, overtimeMinutes }`: the league's row, null `season_id`, holds all but the tiebreakers, and each season's row its `tiebreakers`; it is the one key `transformSeasonData` **merges** field by field (`seasonRules()`) rather than letting the season's row replace the league's. The name is from when it held only timeouts, and keeping it meant no `admin-content` redeploy; a row saved before a field existed gets that field's default). A new key must also be added to `admin-content`'s `validKeys`, which silently skips any other.

### Environment

```
SUPABASE_URL=
SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=
```

Copy `.env.example` to `.env` for local development. The seed script and Edge Functions use `SUPABASE_SERVICE_ROLE_KEY`; the browser uses only `SUPABASE_ANON_KEY`.

The admin password is **not** an `.env` variable: it is the `ADMIN_PASSWORD` Edge Function secret in Supabase (Dashboard → Project Settings → Edge Functions → Secrets) and nowhere else. `auth-login` checks logins against it and `_shared/auth.ts` signs and verifies the admin JWTs with it, so changing it logs every admin out. Never write its value into the repo — not in docs, examples or tests — because the repo is public.

### Deploy Flow

**Two-repo model**: develop and test in this dev repo, then sync/PR into the production fork. GitHub Pages serves the fork's `main` branch at `farajleague.org`. Edge Functions deploy separately to Supabase (not via GitHub Pages). Migrations run via Supabase dashboard or `npx supabase db push` (apply in order 001–016).

`js/config.js` has Supabase URL and anon key baked in — dev and prod share the same Supabase project, so no config change is needed when syncing to the fork.
